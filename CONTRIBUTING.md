# Contributing

Thanks for considering a contribution. Most of what's worth saying lives
elsewhere already — this file is just the pointer.

## Building from source

Either:

- **Open this folder in Android Studio.** Let Gradle sync, hit Run on a device
  or emulator. The Gradle wrapper jar isn't shipped (it's regenerated by
  Android Studio on first sync) so a fresh clone needs the IDE once to
  populate it.

- **Build from the command line.** From the project root:

  ```
  ./gradlew assembleDebug
  # APK ends up at app/build/outputs/apk/debug/app-debug.apk
  ```

  Use `assembleRelease` if the four `RELEASE_*` env vars documented in
  [docs/RELEASE.md](docs/RELEASE.md) are set; otherwise release builds come
  out unsigned.

## Running the debug build via GitHub Actions (no Android Studio)

The repo's `.github/workflows/build.yml` builds a debug APK on GitHub's own
servers on every push to `main`, or on demand. Go to **Actions → "Build
Debug APK" → "Run workflow"** to trigger one, then download the artifact from
the completed run. This is the same path documented in the README's *Install*
section — pointed out here for anyone hacking on the code without a local IDE.

## Reporting bugs / giving feedback

Please [open an issue](../../issues). There's a [bug-report
template](../.github/ISSUE_TEMPLATE/bug_report.md) — filling it in (device,
Android version, what's happening, what you'd expect) is the single biggest
help. The "tested devices" list below is built from what people have reported
so far; if yours isn't there, that's the kind of report that fills it in.

## Coding conventions

The project is small enough that conventions are mostly the ones IntelliJ
defaults to. A few worth noting if you're going to be in the code:

- **Compose for the UI.** No XML layouts except the manifest, the launcher
  icons, and the few theme files that have to be XML.
- **One file per top-level class.** `MainActivity.kt` is the exception, not
  the rule, and it's only that big because the control panel lives there too.
- **Comments are "why", not "what."** If a line of code needs a comment to
  explain what it does, the line should be rewritten until it doesn't. If a
  line needs a comment to explain *why* it's written the way it is — sensor
  conventions, OEM quirks, Android version gates — that's worth keeping.
- **No new dependencies without a PR comment explaining why.** Two of the
  bigger refactors in this repo's history were *removing* dependencies
  (`haze` → `backdrop`, the original Compose BOM bump), so adding one is the
  bigger deal here.
